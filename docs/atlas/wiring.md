# Wiring

The map's runtime wiring (who calls whom, which queue sits between them, which store each component reads) lives in prose on the atlas pages, where it has no schema. A model extracts it, one page at a time, into edges and infrastructure nodes, and deterministic code keeps the result honest: it resolves every endpoint against known ids, drops what does not resolve, rejects nodes that are really details, refuses to publish a map that lost a curated flow or a fifth of a layer, and caches every answer so a model is asked only about what changed. This page describes the extraction, the resolution, the aliases, the flow guard, the committed cache and the rules for re-extraction.

## The pipeline

The map is generated by ordered stages, as much as possible in plain code:

| stage | kind | what it does |
|---|---|---|
| read-atlas | code | parse frontmatter and the stable-id sections of every page, section files included |
| visibility | code | public, internal or private, from the code host |
| components | code | split repositories into the components they ship, from `artifacts` and the workspace's component table |
| build-edges | code | `depends_on` becomes the build layer |
| wiring | model | the `role`, `data` and `interfaces` sections become network, queue and data edges |
| shared-deps | code | a committed snapshot of what each component contains becomes the shared-dependency layer |
| infra | code | environments, delivery nodes and the delivery layer, from the gitops checkout and `deploy` |
| flows | code | the curated journeys in `viz/flows/*.md` |
| resolve | code | canonicalize, resolve every endpoint, drop what does not resolve |
| layout | code | the force simulation, run once, coordinates baked in |
| emit | code | `viz/data/graph.json` and `viz/data/report.json` |

Only the wiring stage calls a model. Everything downstream of it is code, and `flax atlas generate --reuse-wiring` runs the whole pipeline from the cache with no model at all.

## The extraction

The prompt ships with the package (`prompts/extract-wiring.md`; a workspace copy overrides it). It gives the model one page's wiring sections, the repository's own components, and the list of known component ids, and asks for edges on exactly three layers: `network` (a request one component makes to another, caller to callee, third parties included), `queue` (modeled as two edges through the queue itself, producer to queue and queue to consumer, never producer to consumer), and `data` (a component reading or writing a durable store, component to store). Every endpoint is a known component id or an infrastructure node the answer declares with the exact identifier the page uses.

The prompt's central rule decides whether the graph is readable: an infrastructure node is a shared, named, durable system that more than one thing could address (a database, a bucket as one node, a queue or broker, a secrets engine, a published dataset, a distinct third-party service). Everything else is a detail that belongs in an edge's label, not a node of its own: a flag, a path, a single file, an environment variable, a config key, a cluster object name, a prefix inside a store, a feed inside an aggregator, a notification target. The rules: only emit what the page states, never complete the picture from what systems like this usually do; every edge carries an anchor (the path, variable, route or section the page cites); anything the page marks `UNVERIFIED` or hedges is marked `unverified`; no build or library dependencies, those come from frontmatter; no self-edges. The answer is JSON and nothing else.

notes-co's `notes-api` page yields, for instance: `notes-api -> postgres` on `data` anchored to `src/store/db.ts`; `notes-api -> notes-events` and `notes-events -> notes-worker` on `queue` anchored to `src/events/publish.ts`; `notes-web -> notes-api` on `network` anchored to the routes table; `notes-api -> <identity provider>` on `network`, an external node.

## Resolution: the deterministic half

The resolve stage canonicalizes names and resolves every endpoint of every edge:

- **Aliases and canonical names**: the workspace's atlas section carries a table of aliases (several spellings of the same real thing, such as `postgres:16` and `postgres`, or a cluster-internal host name and the service it names) and the canonical name each maps to. A new spelling that fails to resolve is a one-line addition to that table.
- **Generic names and environment tokens**: names that are too generic to be a node, and environment words that belong on an edge label, are stripped.
- **Store merging**: several spellings of one store merge into one node; stores a component owns are marked as owned.
- **Junk infrastructure filter**: a node that is really a CLI flag, a local path, a config key or a cluster object name is rejected and counted in `report.json` under `rejectedInfra`.
- **Dropping**: an edge whose endpoint does not resolve to a real node is dropped and counted under `droppedEdges`, never drawn.
- **The emit floor**: the emit stage refuses to write a graph with fewer nodes or edges than the configured minimum, and the wiring stage throws when more than 30% of pages fail to extract. Both exist because a build once deployed a map with 49 nodes and no connections as a green build, after every extraction failed silently.

Every extracted edge keeps its anchor and its unverified flag, and the viewer shows both, so any claim on the map can be checked against the page that made it.

## Curated flows and the flow guard

Guided flows (a journey animated one hop at a time) are hand-written, one Markdown file per flow in `viz/flows/`, with frontmatter (`id`, `name`, `plane`, `summary`) and one section per step naming `from`, `to`, `layer` and an `anchor`, with the prose shown in the player. A teaching narrative is faster to write than to correct, and the people who know what a journey should say are the ones who should say it. A step whose endpoints do not resolve is dropped and counted.

The flow guard protects the flows from the model. When a page is re-extracted and its new answer makes a curated flow step stop resolving (the answer named the node differently), the page keeps its previous answer and stays queued; the run names the page, the step and the name the new answer used, so a person adds an alias or updates the flow. The new answer stays in the cache, so the run after that fix adopts it without a model call. A step that does not resolve even with every previous answer fails the run.

## The committed cache

Every answer is cached under `viz/cache/` and committed. The cache key hashes the wiring model, the extraction prompt and the page's own wiring sections, section files included; each entry records the model that made it. So:

- a page edit that touches no wiring section re-asks nothing;
- a page edit that touches a wiring section re-asks for that page only;
- a prompt or model change alone re-asks nothing under `--reextract-changed`, and everything under a cold run;
- the map can always be rebuilt from the committed cache with no model and no credential, which is what the deploy workflow does: `build` bundles only and never regenerates.

The cache is content, and it is reviewed like content: the map refresh job's pull request carries the new cache entries beside the data files.

## Re-extraction rules

`flax atlas generate` takes one of three modes:

- `--reuse-wiring`: no model. Every page uses its cached answer; a page with no cache entry gets no extracted edges until someone re-rolls it deliberately.
- `--reextract-changed`: new pages and pages whose wiring sections changed since their answer ask the model, at most a configured number per run (six in the reference job); the rest keep their answer and wait for the next run. The run lists the deferred pages.
- a cold run (`--no-cache`, or a changed model or prompt without the flag above): every page is asked. About ten minutes and a few dollars for a hundred pages.

Calls go two at a time and wait out rate limits. A page the model gives up on after three attempts is asked once of a fallback model when one is configured, before it keeps its previous answer. The model comes from an environment variable, an agents media model socket (the reference job's path), a provider key, or a local coding agent's login; there is no default. `flax atlas wiring-eval` re-extracts a sample of pages with a candidate model and compares its edges with the cached answers, page by page, reading the cache and never writing it; run it before changing the wiring model.

## Keeping it honest

After a significant atlas update, regenerate and skim `viz/data/report.json`. Two numbers are worth a look: `droppedEdges` (a claim whose endpoint did not resolve, often a renamed component) and `rejectedInfra` (detail-level noise the filter caught). A sudden jump in either usually means a page changed shape rather than content. The curated knowledge the resolver carries (aliases, the component table, the tenancy lists where an organization has them) is kept in step with the pages in the same session that changes them; otherwise the map will state, confidently and in color, something the pages no longer say.
